<objective>
Complete the rendering half of SCENE-04: ship the official UR3e robot description and its meshes as build-time assets, load them with the package remap that keeps mesh fetches from silently 404-ing, pose the robot from the kinematics module's exported ready pose, and mount it on a visible 7th-axis rail with end-stop geometry at both travel limits and the carriage parked at travel centre — with honest loading and error states over the canvas.

Purpose: plan 01-02 proved the DH math in isolation against an externally-computed reference; plan 01-01 built the interactive, deployed scene. Neither renders a robot. This plan closes the phase goal — "an accurately-modeled UR3e, including its 7th-axis rail, at a correct static pose" — and it does so without ever letting visual plausibility stand in for correctness: the shipped description is cross-checked against the same DH constants the forward-kinematics test asserted on, and every mesh the description references is proven to exist before the scene is trusted.

Output: a deployed 3D cell with the real UR3e standing on its rail; the asset-integrity test that guards the rendered robot against a substituted or incomplete model; and the load-status surface later phases reuse.
</objective>

**Step 1 — Acquire and commit the assets.** Fetch the flattened, non-xacro UR3e description from the dataset repository and path RESEARCH.md cites, and save it as `public/robots/ur3e/ur3e.urdf`. Do not parse xacro at runtime and do not stand up a xacro toolchain — RESEARCH.md verified this file is the autogenerated flat output and that its joint origins match the official DH table exactly.

Then read the saved description and extract every distinct mesh filename it references. Each is of the form `package://ur_description/<rest>`. For each one, fetch the corresponding file from the upstream official robot-description package and write it to `public/robots/ur3e/<rest>` — mirroring the path segment that follows the package name exactly. This mirroring is the whole point: the loader remaps the package name to the public directory, so the on-disk layout below that directory must match the description's paths character for character or the meshes fetch a 404 while the description itself parses cleanly and the robot renders as bare joints. Commit the description and every mesh into the repository so the deployed bytes are pinned in git history rather than re-fetched at build time from a third party.

**Step 2 — Load and pose the robot.** Create `src/scene/RobotModel.tsx`. Construct the loader manually with `new URDFLoader()` and assign `loader.packages = { ur_description: '/robots/ur3e' }` **before** calling `loader.load` — the one-line loader hook form does not allow this and is the direct cause of the 404 pitfall above. Call load with the description path, an on-load callback, and an on-error callback (the third positional slot is progress; pass through or omit it, but do not drop the error handler — task 2 wires it).

In the on-load callback, before handing the robot to the scene:
- Rotate the loaded robot -90 degrees about the x axis. The description uses a z-up frame and the scene is y-up; without this the arm renders lying on its side. Rotating about x preserves the world x axis, so the rail translation direction stays consistent with the kinematics module's rail convention.
- Apply the display pose by walking the two exported constants together: for each index, call the robot's per-joint setter with `UR3E_JOINT_NAMES[i]` and `UR3E_READY_POSE[i]`, both imported from the kinematics barrel. Use the ready pose, never the home pose — D-08 splits the displayed pose from the asserted pose deliberately, and the home pose renders as a flat silhouette.
- Leave the flange bare. D-03 puts the print head and mill spindle in Phase 7; do not attach placeholder tool geometry.

Render the loaded robot as a primitive scene-graph object, and render nothing while it is still loading. Do not fall back to primitive stand-in geometry on failure — an empty slot plus task 2's error state is the honest outcome; a plausible-looking fake is the failure mode this plan's prohibition forbids.

**Step 3 — Build the rail rig.** Create `src/scene/RailRig.tsx` importing `RAIL_TRAVEL` and `RAIL_CENTER_X` from the kinematics barrel. Render, per D-02 and D-07:
- A track mesh running along the world x axis, spanning the full travel range with a small overhang past each limit so the end-stops sit on the track rather than floating past its ends, low and flat enough to read as a linear rail rather than a plinth.
- Two end-stop meshes, one positioned at `RAIL_TRAVEL.min` and one at `RAIL_TRAVEL.max`, tall enough to be visible from the default camera framing — these are the visual anchor Phase 5's remaining-travel readout will be read against.
- A carriage group positioned at `RAIL_CENTER_X` along x and sitting on top of the track, containing `RobotModel` as its child (D-09: the static pose parks the carriage at travel centre so travel remains visible in both directions).
Give the track and both end-stops the UI-SPEC Secondary tone so they recede behind the robot; the Accent tone is reserved for the nav cube and the reset CTA and must not appear on rail or robot geometry. Take every rail dimension that relates to travel from the imported constants — do not restate a bound as a numeric literal in this file, because the rail geometry and Phase 5's telemetry must be provably reading one definition.

**Step 4 — Mount it.** Edit `src/scene/CellScene.tsx` to render `RailRig` at the insertion point plan 01-01 reserved, keeping the existing composition order: lights, floor, rail rig, controls, nav cube, reset listener. Confirm the robot sits on the floor plane rather than intersecting or floating above it, and that the default camera framing still centres the cell now that the rig occupies it — the robot is the scene's focal point per the UI-SPEC, so adjust the shared framing constants in `src/scene/camera-defaults.ts` only if the rig does not fit the frame with comfortable margin, and never by hardcoding a second framing.
