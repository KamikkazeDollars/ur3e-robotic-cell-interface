## Verified IK port contract (planner spike, run this session)

`03-RESEARCH.md` Assumption **A3** explicitly required re-verifying its condensed code example against
`ur_kin.cpp` before use. That verification was performed during planning by porting the algorithm against
this repository's real `UR3E_DH` table and `forwardKinematics` chain and round-tripping it over 400
randomised poses. **Three findings are load-bearing and must not be rediscovered by trial and error.**

**Finding 1 — do NOT apply `ur_kin.cpp`'s base-frame index remapping.** `ur_kin.cpp`'s `forward()`
emits its matrix in a ROS base frame that is rotated relative to this project's raw standard-DH chain.
Its `inverse()` therefore reads permuted, sign-flipped elements of the caller's matrix. This project's
`forwardKinematics(...).matrix` **is** the raw DH chain, so the solver must read `target[row][col]`
**directly**, with no permutation and no sign flips.

<!-- planner-discipline-allow: T02 = -T[0][0] -->

| Port variant | Round-trip result (400 random poses) |
|---|---|
| With `ur_kin.cpp`'s remap (e.g. `T02 = -T[0][0]`, `T00 = T[0][1]`, `T22 = T[2][0]`) | **0 / 400 pass**, worst TCP error **1.12 m** |
| Reading `target[row][col]` directly | **400 / 400 pass**, worst TCP error **3.7e-16 m** |

The remapped variant is precisely `PITFALLS.md` Pitfall 1 / `03-RESEARCH.md` Pitfall A's failure mode:
it produces confident, plausible-looking poses that are metres wrong. The round-trip test in Task 2 is
the gate that catches it.

**Finding 2 — the `theta1` three-case branching (resolves A3).** Solve order is
θ1 (2 branches) → θ5 (2 per θ1) → θ6 → θ3 (2, elbow up/down) → θ2 → θ4, yielding up to 8 solutions.
With `A = d6*T[1][2] - T[1][3]`, `B = d6*T[0][2] - T[0][3]`, `R = A*A + B*B` and `ZERO_THRESH = 1e-8`:

| Case | Condition | θ1 branches |
|---|---|---|
| Degenerate A | `abs(A) < ZERO_THRESH` | `asin(div)` and `PI - asin(div)`, where `div = -d4/B`, or `-sign(d4)*sign(B)` when `abs(abs(d4)-abs(B)) < ZERO_THRESH` |
| Degenerate B | `abs(B) < ZERO_THRESH` | `acos(div)` and `2*PI - acos(div)`, where `div = d4/A`, or `sign(d4)*sign(A)` when `abs(abs(d4)-abs(A)) < ZERO_THRESH` |
| Unreachable | `d4*d4 > R` | none — return an empty array |
| General | otherwise | `acos(d4/sqrt(R)) + atan2(-B, A)` and `-acos(d4/sqrt(R)) + atan2(-B, A)` |

θ5 uses `numer = T[0][3]*sin(θ1) - T[1][3]*cos(θ1) - d4` and both of `acos(numer/d6)`, `2*PI - acos(numer/d6)`.
θ6 is undetermined when `abs(sin θ5) < ZERO_THRESH` (wrist singularity) — emit `0` there and let the
caller's continuity rule choose among branches, per D-03. θ3 is rejected when `abs(c3) > 1`.
Every `acos`/`asin` argument is clamped to `[-1, 1]` before the call (ASVS V5, `T-03-01`).

**Finding 3 — empirical behaviour on this project's real geometry.** Measured against the Phase 2
anchor (`ROBOT_MOUNT_WORLD = {x: 0, y: 0.19, z: 0.5}`, `TOOLPATH_ANCHOR ≈ {x: 0, y: 0.413, z: 0.81}`):

| Property | Measured |
|---|---|
| Tool-down targets reachable over the print sample's 150 mm span (7×7 grid, and again lifted 3 mm for upper layers) | 49/49 and 49/49 |
| Tool-down targets reachable over the mill sample's 120 mm span | 49/49 |
| In-limit branches available per toolpath point | 4 to 8 |
| Largest adjacent joint-space step over a 160-sample 150 mm square perimeter, nearest-branch selection | **0.035 rad** (~2°) — no visible snapping |
| Rail optimum for the anchored sample | **0.0000** (= `RAIL_CENTER_X`), worst reach 0.4513 m vs the 0.5 m envelope |
| Rail optimum for the same toolpath translated +1.0 m in X | **1.0050** — the rail visibly moves, so the heuristic is not vestigial (D-02) |
| Joint-space distance from `UR3E_READY_POSE` to the first sample's nearest branch | **3.53 rad** |

That last row is expected and must **not** be "fixed": the ready pose parks the arm in the air and the
first toolpath point is on the workbench, so loading a sample legitimately moves the arm a long way once.
It is a one-time repositioning, not a mid-scrub snap, and clamping it would misrepresent the pose.

**A1 detail.** The IK target's rotation submatrix is the constant `Rot_x(PI)` — rows `[1,0,0]`,
`[0,-1,0]`, `[0,0,-1]`. Its third column `(0,0,-1)` puts the flange approach axis along DH −Z, which is
scene −Y, i.e. straight down onto the workbench; the flange X axis is DH +X (scene +X) and never varies.
The tangent-derived-X variant `03-RESEARCH.md` floated was evaluated and **rejected**: at a square
perimeter's corner the path tangent changes discontinuously between adjacent samples, which would rotate
wrist_3 by ~90° in a single sample step. D-03's continuity rule selects among branches *of a given
target* and cannot smooth a discontinuity in the target itself, so a tangent-derived X axis would
manufacture exactly the visible snapping this phase's first success criterion forbids.

into the half-open interval that spans from minus pi (exclusive) to pi (inclusive). Return an empty array
for an unreachable target rather than throwing.

Export `jointSpaceDistance(a: JointAngles, b: JointAngles): number` as the Euclidean norm of the
component-wise difference.

Export `validBranches(candidates: JointAngles[]): JointAngles[]`, keeping only branches where every angle
satisfies `Number.isFinite` **and** the tuple passes the existing `isWithinJointLimits`. Order matters and
must be documented: the finiteness screen runs first so a non-finite value produced by a near-singular
division can never reach a comparison operator, where it would silently compare false and be discarded
for the wrong reason (ASVS V5, `T-03-01`).

Export `pickClosestBranch(candidates: JointAngles[], previous: JointAngles): JointAngles | null`,
returning the candidate minimising `jointSpaceDistance` to `previous`, or `null` for an empty candidate
list. Document that this is D-03's continuity rule and that it belongs here as a pure function while the
decision of *what* `previous` is belongs to the compiler.

**Step 2 — extend `src/kinematics/rail.ts` with `resolveRailPosition`.** Signature:
`resolveRailPosition(points: readonly [number, number, number][], mount: { x: number; y: number; z: number }): number`.
Take `mount` as a parameter rather than importing `ROBOT_MOUNT_WORLD`, because `toolpath-anchor.ts`
already imports from this module and the reverse import would close a cycle.

Implement D-02 as a brute-force scan: export `RAIL_RESOLUTION_CANDIDATES = 201`, evaluate that many

candidate compute the largest 3D distance from the candidate's mount position to any toolpath point. The
candidate's mount position is the given `mount` with its x replaced by `mount.x + (candidate - RAIL_CENTER_X)`,
so the function stays correct if the mount ever stops coinciding with the travel centre. Return the
minimising candidate passed through the existing `clampRailPosition`. Return `RAIL_CENTER_X` for an empty
point list.

**Step 5 — `src/trajectory/compile.ts`.** This is the orchestrator; it is the only module in the
codebase permitted to convert a toolpath point into an IK target.

Export `sceneToDhFrame(point: readonly [number, number, number], mount: { x: number; y: number; z: number })`
returning `{ x: point[0] - mount.x, y: -(point[2] - mount.z), z: point[1] - mount.y }`, and its exact
inverse `dhFrameToScene(dh, mount)` returning `[dh.x + mount.x, dh.z + mount.y, mount.z - dh.y]`. Both
carry a comment citing `toolpath-anchor.ts`'s documented composition and `RobotModel.tsx`'s frame
rotation. State that these are the single conversion site: solving against raw scene coordinates produces
a confidently wrong pose because both frames are metric and roughly co-located, which is Pitfall A's
exact failure mode.

Export `TRAJECTORY_SAMPLE_SPACING_M = 0.002` (one solve per 2 mm of path) and
`MAX_TRAJECTORY_SAMPLES = 4000`, both with comments explaining the choice: 2 mm keeps the flange visibly
on the drawn line at the bundled samples' roughly 150 mm scale, and the ceiling bounds compile cost
independently of Phase 2's own segment ceiling.

Export the result types:
`type TrajectoryStatus = 'ready' | 'frozen-at-unreachable'`;
`interface TrajectorySample { scrubFraction: number; point: [number, number, number]; joints: JointAngles; railPos: number; tcpPosition: { x: number; y: number; z: number } }`;
`interface CompiledTrajectory { samples: TrajectorySample[]; railPos: number; status: TrajectoryStatus; requestedSampleCount: number }`.
Note on `TrajectorySample` that plan 03-02 adds a `singularityFlags` field, so consumers should not
assume the shape is final within this phase.

Export `compileTrajectory(toolpath: ParsedToolpath): CompiledTrajectory`, pure and synchronous, never
throwing. It: flattens the points; returns an empty-sample `ready` result when fewer than two distinct
points survive; builds the arc-length table; resolves one rail position for the entire toolpath via
`resolveRailPosition(points, ROBOT_MOUNT_WORLD)` — computed once, before any solve, per D-01; derives
`sampleCount` as the path length divided by the spacing, rounded up, plus one, bounded to at least two
and at most `MAX_TRAJECTORY_SAMPLES`; then walks `i` from zero to `sampleCount - 1` computing
`scrubFraction = i / (sampleCount - 1)`.

For each sample: take the task-space point via `pointAtFraction`; convert it with `sceneToDhFrame` against
`ROBOT_MOUNT_WORLD`; make it arm-relative by subtracting `railPos - RAIL_CENTER_X` from its x component
only, mirroring the pure prepended `transX` translation `forwardKinematics` composes the rail as; build
the target with `buildToolDownTarget`; call `solveUR6IK`; filter with `validBranches`; and select with
`pickClosestBranch` against the previous accepted sample's joints, seeded from `UR3E_READY_POSE` for the
very first sample. Record `tcpPosition` as `forwardKinematics(joints, railPos - RAIL_CENTER_X).tcpPosition`
so every sample carries an FK-verified readout rather than a re-derivation.

D-06 handling: the first sample with no valid branch stops the walk. Return the samples accumulated so
far with status `frozen-at-unreachable` and `requestedSampleCount` set to the count the compiler
intended, so a consumer can tell a complete trajectory from a truncated one. Never throw and never
substitute an approximate pose.

Add a comment recording the anti-pattern this module must never adopt: sampling density comes from
solving more task-space points, never from blending two already-solved joint tuples, because blended
joint values trace a bowed path in task space even when both endpoints are individually correct
(Pitfall 13).
