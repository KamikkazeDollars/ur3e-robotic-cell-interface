<objective>
Close G-03-4's two in-scope items: make the toolpath's start/end markers proportional to the toolpath
instead of a fixed absolute size, and give each marker a clearly visible vertical guide down to the
workbench.

Purpose: the marker radius is a hardcoded 0.012m. The bundled print sample spans 150mm per side and the
mill sample 120mm, so each marker renders at 24mm across — 16% and 20% of the whole path's extent
respectively. That is why they read as oversized. `ParsedToolpath.bounds` is already computed and
currently unused for sizing; deriving from it makes the markers correct at any sample scale rather than
correct at one. The second half of the report — that the vertical line a point sits on is hard to see —
has no existing implementation at all: there is no guide-line component, so the user was reading
ordinary plunge and rapid segments as if they were anchors.
Output: a pure sizing module with its own test, proportional markers, and a stem-plus-footprint guide
under each one.
</objective>

<scope_boundary>
**This plan does NOT change how many markers render.** The user's report bundled a third complaint —
three operations exist but only two points show. Two markers is the current design: the toolpath is one
continuous parsed path with an overall start and an overall end, and per-operation markers require
operation-grouping data that exists nowhere in the pipeline (`ClassifiedSegment`, `ParsedToolpath` and
`CompiledTrajectory` all lack it). ROADMAP Phase 6 owns that work — "User sees a distinct start and end
marker on the 3D trajectory for each operation" is its first success criterion, under SIM-03/SIM-06.
The user explicitly confirmed on 2026-08-15 that marker count stays deferred and only sizing and guide
visibility are fixed now.

Do not add operation grouping, do not add a third marker, and do not add click-to-jump on markers
(that is UAT test 5's deferred follow-up). Anything that changes the marker COUNT is out of scope.
</scope_boundary>

Export these constants, each with a comment giving its rationale:

| constant | value | rationale to record |
|---|---|---|
| `MARKER_RADIUS_FRACTION` | `0.02` | fraction of the toolpath's largest axis span; puts the marker's diameter at 4% of the path's extent — a bullet point on the path rather than a feature competing with it |
| `MIN_MARKER_RADIUS` | `0.0015` | floor for a degenerate or absent bounding box, so a marker is always visible instead of collapsing to a zero-radius sphere |
| `MAX_MARKER_RADIUS` | `0.01` | ceiling for an implausibly large path, below the previous hardcoded value so this change can never make markers larger than they already were |
| `SCRUB_MARKER_SCALE` | `1.75` | the scrub indicator stays the primary marker; this preserves the size hierarchy the previous absolute constants encoded, now at every path scale |
| `GUIDE_STEM_RADIUS_RATIO` | `0.35` | the vertical guide reads as a stem the marker sits on, thinner than the marker itself |
| `GUIDE_FOOTPRINT_RADIUS_RATIO` | `2.5` | the tabletop footprint under the stem is wider than the marker, so the anchor stays legible even where the stem is barely taller than the marker's own radius |
| `GUIDE_FOOTPRINT_LIFT` | `0.0005` | half a millimetre above the tabletop, enough to avoid z-fighting with the opaque slab without visibly floating |
| `MIN_MARKER_CONTRAST` | `2` | the contrast floor the marker and guide tones must clear against the workbench surface they are drawn on |

Export a small internal helper `largestSpan(bounds)` returning the maximum of the three per-axis
`max - min` differences, or `0` when bounds is null.

Export `markerRadiusFromBounds(bounds: ParsedToolpath['bounds']): number` — multiply the largest span by
`MARKER_RADIUS_FRACTION`, then clamp into `[MIN_MARKER_RADIUS, MAX_MARKER_RADIUS]`. Write the clamp so a
null, zero or non-finite span lands on the minimum rather than propagating; a `NaN` must never reach a
geometry argument, where it would silently blank the mesh.

Export `scrubMarkerRadiusFromBounds(bounds)` returning `markerRadiusFromBounds(bounds) * SCRUB_MARKER_SCALE`.
Note in its comment that it deliberately multiplies the endpoint radius rather than clamping
independently, which is what makes the hierarchy hold at every scale by construction rather than by
two constants that happen to be ordered correctly today.

Export `guideStemRadius(markerRadius)` and `guideFootprintRadius(markerRadius)` applying their ratios.
