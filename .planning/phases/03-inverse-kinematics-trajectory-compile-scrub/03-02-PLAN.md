  <action>
**Step 1 — `src/kinematics/singularity.ts`.** A framework-free module in the same style as
`forward-kinematics.ts`: no React, no Three.js, no store import.

Export `SINGULARITY_ANGLE_EPSILON = 0.05` (radians, roughly three degrees) and
`SINGULARITY_DISTANCE_EPSILON = 0.02` (metres). Document both plainly as chosen heuristic thresholds
tuned for a visual proximity warning, not values sourced from a Universal Robots specification — the same
honesty the rail module already applies to its own travel range. A reader must not mistake them for
datasheet numbers.

Export `interface SingularityFlags { wrist: boolean; shoulder: boolean; elbow: boolean; any: boolean }`
and `classifySingularity(joints: JointAngles): SingularityFlags`, a pure function mirroring
`isWithinJointLimits`'s shape but returning a flags object. Implement the three families from the
Singularities table:

- Wrist: the absolute value of joint 5 is below the angle epsilon, meaning the joint 4 and joint 6 axes
  have become collinear and rotation about them is degenerate.
- Elbow: the absolute value of joint 3 is below the angle epsilon, or within the angle epsilon of pi,
  meaning the arm is fully extended or fully folded.
- Shoulder: the wrist centre lies on the joint-1 rotation axis. Take the wrist centre as the translation
  of `forwardKinematics(joints).frames[3]`, and its distance from the joint-1 axis as the planar
  magnitude of that translation's x and y components — the joint-1 axis is the base z axis in this DH
  chain. Compare against the distance epsilon. Comment the derivation, because "distance from the
  joint-1 axis" is otherwise not obviously the planar magnitude of the first two components.

Set `any` to the disjunction of the three. Document at the top of the file that this is D-08: the
detection is built in this phase while the IK work is fresh, deliberately ahead of the Phase 5 Dashboard
that will display it, and that nothing in Phase 3 renders these flags.

**Step 2 — `src/kinematics/index.ts`.** Re-export `classifySingularity`, the `SingularityFlags` type and
both epsilon constants from `./singularity`, keeping the existing barrel ordering and comment style.

**Step 3 — `src/trajectory/compile.ts`.** Add `singularityFlags: SingularityFlags` to `TrajectorySample`
and populate it by calling `classifySingularity` once per accepted sample, immediately after the branch
is selected and alongside the existing `tcpPosition` readout. Remove the note added in 03-01 warning that
the sample shape is not yet final, since it now is. Do not let a singular classification affect branch
selection or acceptance in any way — it is an observation recorded about the chosen pose, never a filter.
Comment that distinction explicitly, because a future reader could reasonably assume flagged samples were
meant to be rejected.

**Step 4 — `src/trajectory/compile.test.ts`.** Extend the existing suite: assert every compiled sample
carries a `singularityFlags` object with all four boolean fields present, and that `any` agrees with the
disjunction of the other three across the whole sample array. Do not assert that the bundled-sample
geometry produces any particular flag value — the toolpath is not constructed to pass through a
singularity, so pinning a specific outcome would encode an accident of the sample rather than a contract.
