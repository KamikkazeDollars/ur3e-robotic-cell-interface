<objective>
**As a** person watching the toolpath play back, **I want to** see the arm and the
position marker glide along the path, **so that** the simulation reads as real
motion instead of a sequence of discrete jumps between precomputed stills.

This slice expands the tracer outward along the second axis: the position value
the scene reads is unchanged, but how that value is turned into a pose becomes
continuous instead of snapping to the nearest precomputed sample.

Purpose: playback advances by *time*, not by drag distance, so it lands on
arbitrary fractions between samples — and a short toolpath can compile to very few
samples. Rounding to the nearest sample was invisible during manual scrubbing on a
dense path; under a continuous clock it becomes visible ticking. This also
supersedes a Phase 3 decision on purpose (recorded in STATE.md): `ScrubMarker.tsx`
currently duplicates `RobotPose.tsx`'s index derivation verbatim so the two can
never drift apart. A single shared function enforces that same invariant more
strongly than two copies, so the duplication is replaced rather than preserved —
record that reversal in the plan summary.

Output: a pure, unit-tested interpolated sample lookup, with both per-frame scene
consumers refactored onto it.
</objective>

  <action>
Create `src/trajectory/sample-lookup.ts` as a pure, framework-free module — same
discipline as `src/trajectory/arc-length.ts`, with a header comment stating it
imports no rendering engine, no store, and no UI.

Export an interface `InterpolatedSample` carrying exactly two fields: `point` as a
three-number tuple and `joints` typed as `TrajectorySample['joints']`. Deliberately
omit `railPos`, `tcpPosition`, and `singularityFlags` — those are per-sample
observations of a solved pose, and a blended value for them would be a fabricated
reading rather than an interpolated position. Document that omission.

Export `sampleAtFraction(trajectory: CompiledTrajectory, fraction: number): InterpolatedSample | null`.
Return `null` when `samples` is empty. Coerce a non-finite `fraction` to 0, then
clamp into [0, 1] using the same shape the store's setter uses. Locate the
bracketing pair with a binary search over `samples[i].scrubFraction`, which
`compile.ts` guarantees is monotonically non-decreasing: narrow `lo`/`hi` until
they meet on the first sample whose `scrubFraction` is greater than or equal to
the clamped fraction, take that as the upper sample, and take the sample one index
below it (floored at 0) as the lower. Compute the pair's span, treat a span below
1e-12 as a ratio of 0 rather than dividing, and — this is load-bearing — clamp the
computed ratio into [0, 1] before blending. Without that clamp, a truncated
trajectory whose last sample sits below `scrubFraction` 1 would extrapolate past
its final solved pose when asked for fraction 1, presenting the arm in a
configuration that was never solved and that the robot cannot reach.

Blend both the three-element point and the six-element joint tuple element-wise by
that ratio, and cast the results back to their tuple types. Add a comment
recording why blending in joint space is acceptable here specifically: adjacent
compiled samples are one IK solve every two millimetres of path and are
continuity-selected, so the difference between blending in joint space and in task
space is sub-visual — this is not the case of blending two solved poses that are
far apart, which traces a bowed path the arm never follows and which
`compile.ts`'s own doc comment forbids the compiler from doing. State that the
lower and upper samples must always be immediate neighbours in the array, which
the binary search guarantees by construction.

Write `src/trajectory/sample-lookup.test.ts` before the implementation, covering
every item in the `<behavior>` block, following the project's
`describe('<subject> — <feature>', ...)` convention.
