<objective>
**As a** person watching the toolpath play back, **I want to** see the path light up
behind the tool as it is traversed, **so that** I can tell at a glance how far
through the job the robot is and which part of the path it has already run.

Gap closure for **G-04-1** (04-UAT.md, test 1). ROADMAP Phase 4 success criterion 2
calls for a *trajectory highlight* **and** a TCP marker tracking playback. Only the
marker was ever built (Phase 3's `ScrubMarker.tsx`), and at roughly 5mm radius
against a 150mm path swept in ten seconds it is easy to miss — the user reported
seeing nothing at all during or after a run. `Toolpath.tsx` renders a static,
playback-agnostic line and never reads the playback fraction.

This plan expands the existing Phase 4 tracer outward: the clock, the fraction
channel, and the shared sample lookup are unchanged — what changes is that the
drawn path now *reflects* that fraction, and the existing marker becomes legible at
full playback speed.

Purpose: the phase's headline behaviour ("press Play and watch it run") currently
has no visible progress indication on the path itself, which is what made the UAT
run unreadable.

Output: a pure, unit-tested trail-progress module; a highlight component driven
imperatively per frame; a corrected scene mount order; a larger, gated scrub marker.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| playback fraction → line geometry instance count | A non-finite or out-of-range fraction becomes an integer written straight onto an `InstancedBufferGeometry`'s draw count; a negative or oversized value is passed to the GPU draw call rather than being rejected by three.js. |
| compiled trajectory → highlight polyline | The trail's point array is built from compiler output; a trajectory with zero or one usable toolpath sample would otherwise construct a degenerate line whose segment count is zero or negative. |

No new network calls, no new persisted data, no new user-supplied input surface.
No package-manager installs occur in this plan, so the package-legitimacy gate does
not apply.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-11 | Tampering | `traversedSegmentCount` → `geometry.instanceCount` | medium | mitigate | Coerce a non-finite fraction to 0 before any arithmetic and clamp the computed count into `[0, points.length - 1]`, so the value written to the draw count is always a finite in-range integer. Asserted by the NaN/Infinity/-1/2 cases and the boundary cases in `trail-progress.test.ts`. |
| T-04-12 | Denial of Service | degenerate trail geometry | low | mitigate | `buildTrailGeometry` returns null whenever fewer than two toolpath points survive, and the component renders nothing in that case — no zero- or negative-segment line is ever constructed. Asserted by the null/empty/one-point cases. |
| T-04-13 | Denial of Service | per-frame highlight update | low | accept | The frame callback performs a binary-free constant-time arithmetic mapping and writes one integer and one boolean onto objects that already exist. No geometry, material or vector is allocated per frame, so PITFALLS.md Pitfall 12's per-frame recreation leak does not apply. |
| T-04-14 | Information Disclosure | highlight overstating progress | low | mitigate | The segment count floors rather than rounds, so the highlight's leading end never runs ahead of the position the arm actually holds — a highlight that claimed traversal the robot had not performed would misrepresent the simulation. Asserted by the mid-span and real-fixture no-overshoot cases. |
