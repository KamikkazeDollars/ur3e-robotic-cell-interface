<objective>
**As a** person watching the cell run a toolpath, **I want to** see the robot rip
through the non-cutting rapid moves and slow down for the actual cuts, **so that**
the animation reads like a real machine doing real work rather than a marker
sliding along a wire at constant speed.

This slice expands the tracer outward along one axis only: the `FractionMapping`
seam plan 04-01 defined stays exactly the same shape, and its uniform
implementation is replaced by the D-02 move-type-weighted one. Nothing else about
the clock, the store, or the scene changes.

Purpose: deliver D-02 (rapids consume proportionally less of the fixed playback
duration than cuts) on real data, and close the one data-contract gap that made it
impossible — `CompiledTrajectory` carries no travel-vs-toolpath split, so nothing
downstream could tell where on the `scrubFraction` axis the prepended travel move
ends and the g-code's own path begins.

Output: `travelLength`/`toolpathLength` on the compiled trajectory contract, a pure
unit-tested weighted duration mapping, and the clock wired onto it.
</objective>

**Create `src/playback/duration-mapping.ts`** as a pure, framework-free module —
same discipline as `src/trajectory/arc-length.ts`, with a header comment stating
it imports no rendering engine, no store, and no UI, and that it exists so D-01's
fixed duration and D-02's weighting are independently unit-testable.

Export two named constants: `RAPID_SPEED_WEIGHT = 4` and `CUT_SPEED_WEIGHT = 1`.
The semantics are traverse speed, not time cost: playback time for a stretch of
path is its arc length divided by the weight in force, so the larger weight
belongs to rapids and produces less consumed time per unit distance. Document that
direction explicitly on the constants, because the inverted reading (naming these
as time weights and giving rapids the smaller number) yields the exact opposite of
D-02 while still looking plausible. Document that the 4:1 ratio is a deliberately
qualitative, tunable choice — D-01 already establishes this phase does not aim for
physical accuracy, since the g-code's own feed rates are discarded — and that it
can be retuned without touching anything else.

Export `buildDurationMapping(toolpath: ParsedToolpath, trajectory: CompiledTrajectory): FractionMapping`,
implementing the `FractionMapping` interface imported from `./clock-step`; do not
declare a competing local interface. Build it as a monotone breakpoint table
mapping the compiled `scrubFraction` axis onto a weighted-time axis:

- Compute `boundaryFraction = travelLength / (travelLength + toolpathLength)`,
  falling back to 0 when that denominator is below 1e-12. This is the point on the
  `scrubFraction` axis where the prepended travel move ends and the g-code's own
  path begins — read from the contract Task 1 published, never re-derived by
  matching point coordinates.
- The travel phase is weighted at `RAPID_SPEED_WEIGHT` throughout: it is a
  synthetic, non-cutting repositioning move that CONTEXT.md's decisions do not
  address, and treating it as a rapid matches both its purpose and the visual
  language it already borrows. Record that choice in a comment as a deliberate
  assumption, not a derived fact. Its weighted time is
  `travelLength / RAPID_SPEED_WEIGHT`, and it contributes a single linear span
  from `(scrubFraction 0, weightedTime 0)` to
  `(scrubFraction boundaryFraction, weightedTime travelWeightedTime)` — one span
  is exact because the whole phase carries one weight.
- The toolpath phase walks `toolpath.segments` in file order, and within each
  segment walks consecutive point pairs, accumulating the Euclidean distance
  between them and adding `distance / weight` to the weighted time, where `weight`
  is `RAPID_SPEED_WEIGHT` for a segment whose `type` is `'rapid'` and
  `CUT_SPEED_WEIGHT` otherwise. Skip pairs whose distance is below 1e-12 rather
  than emitting a zero-width breakpoint. Push one breakpoint per accepted pair.
- Normalize the toolpath phase's cumulative distances by the walk's own running
  total, then map each onto the compiled axis as
  `boundaryFraction + normalized * (1 - boundaryFraction)`; normalize all weighted
  times by the grand total weighted time. Guard both denominators with the same
  1e-12 floor.
- Return `UNIFORM_FRACTION_MAPPING` unchanged when the table ends up with fewer
  than two breakpoints or the total weighted time is below the floor — a
  degenerate toolpath still plays, uniformly, instead of producing NaN.

Implement both directions with one shared, parameterized bracketing-pair helper
rather than two near-identical search functions: given the breakpoint array, the
key to search on, the key to read out, and a target value, find the bracketing pair
by walking (or binary-searching) the monotone key and return the linear blend of
the read-out key. `elapsedToFraction(elapsedSeconds)` clamps
`elapsedSeconds / PLAYBACK_TOTAL_DURATION_SECONDS` into [0, 1], resolves it against
the weighted-time key, and returns the corresponding `scrubFraction`, returning
exactly 1 when the clamped input is 1 so D-06's terminal frame lands on the last
sample exactly. `fractionToElapsed(scrubFraction)` clamps its input into [0, 1],
resolves it against the `scrubFraction` key, and multiplies the resulting weighted
time by `PLAYBACK_TOTAL_DURATION_SECONDS`. Both directions must coerce a
non-finite argument to 0 before any arithmetic, and both must return a finite
value for every input.

**Wire it into `src/playback/usePlaybackClock.ts`.** Inside the existing
