<objective>
**As an** operator looking at the printing tab, **I want to** be offered printing
g-code only, **so that** the sample picker reflects which tool the cell is
configured for instead of offering jobs the mounted tool cannot run.

Gap closure for **G-04-1** (04-UAT.md, test 1, `missing` item 4). The user asked:
"Let the user choose only the g-code sample for printing when the printing tab is
on, and the same for milling." `SampleSelect.tsx` currently renders every entry in
`GCODE_SAMPLES` unconditionally and never reads `cellMode`; `GcodeSample` has no
mode field to filter on.

This also lays the groundwork plan 04-06 builds on: it introduces the shared
`CellMode` type module that lets domain data and kinematics carry a mode without
either importing the UI store.

Purpose: the mode bar currently changes a chip label and nothing else, so the two
modes are indistinguishable in practice. Filtering the picker is the first place
the mode selection has real consequences.

Output: mode-tagged sample metadata with pure filtering helpers, a filtered
dropdown, and a mount-level hook that keeps the selection and the mode in step.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cell mode (UI chrome store) → sample selection (simulation store) | A mode change now triggers an async fetch/parse/compile in `cellStore`; a change dispatched repeatedly or during an in-flight load could otherwise race a previous selection. |
| sample id → `GCODE_SAMPLES` lookup | The filtering helpers resolve ids supplied by the picker and by the sync hook; an id with no matching entry must not throw or silently pass a mode check. |

No new network calls beyond the existing bundled-sample fetch, no new persisted
data, no new user-supplied input surface. No package-manager installs occur in this
plan, so the package-legitimacy gate does not apply.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-15 | Tampering | `sampleMatchesMode` on an unresolved id | medium | mitigate | Resolve through `GCODE_SAMPLES.find` and return false for an unknown id, so an id that matches no entry can never be treated as belonging to the active mode. Asserted by the unknown-id cases in `samples.test.ts`. |
| T-04-16 | Tampering | mode-change-triggered reselection racing an in-flight load | medium | accept | `cellStore.selectSample` already increments a module-scoped request id and discards any superseded response on both its success and failure paths (T-02-10). A rapid mode toggle therefore lands on the last dispatched selection, which is the intended one; no new guard is added and none is needed. |
| T-04-17 | Denial of Service | mode-change effect re-entering | low | mitigate | The effect is keyed on `cellMode` alone, reads the current selection non-reactively via `getState()`, and returns early when the mode is unchanged from the previous run — so it cannot re-fire on its own selection write or loop on mount. |
| T-04-18 | Information Disclosure | picker offering a job the mounted tool cannot run | low | mitigate | Options are derived from `samplesForMode(cellMode)` rather than the full list, and a mismatched loaded sample is replaced on mode change, so the displayed mode and the running job cannot disagree. |
</threat_model>
