<objective>
Deliver the phase's tracer slice: a user picks a bundled g-code sample from a dropdown and the 3D cell
immediately shows that file's toolpath as a static, colour- and dash-coded line, anchored in front of the
robot. One path, wired through every layer this phase touches — bundled asset, fetch, parse, classify,
anchor, render, mount — with the production build proving the parser stack survives Rollup.

**Phase goal (ROADMAP.md, verbatim):** "Users can upload a g-code file and see it parsed into a
classified, color-coded toolpath rendered in the 3D scene, independent of any kinematics/animation risk."

**Scope note on "upload":** locked decision D-01 replaces file upload with curated, bundled samples for
this phase — REQUIREMENTS.md already scopes out general-purpose g-code authoring/upload, and a bundled
set removes the risk of an unvetted file hitting a parser edge case during a live demo. The user
decision governs; nothing in this phase builds an upload control.

Purpose: prove the whole pipeline end-to-end on one file before expanding to arcs, a second sample,
camera framing, and error surfaces. If the architecture is wrong, it is wrong after one commit rather
than after five.
Output: a working print-sample toolpath in the cell, plus the parser contract and the D-06 anchor
constant that plans 02-02, 02-03 and Phase 3 all build on.
</objective>

**Step 1 — dependencies and the Vite Node-builtin polyfill.** Run `npm install gcode-toolpath@^3.0
gcode-parser@^2.2` and `npm install -D vite-plugin-node-polyfills@^0.28`. In `vite.config.ts`, import
`nodePolyfills` from `vite-plugin-node-polyfills` and add it to the existing `plugins` array alongside
`react()` and `tailwindcss()`, configured with `include: ['stream', 'events', 'timers']`. Do not add
`fs` to that list — the filesystem-backed entry points are never called in this app and leaving `fs`
externalised keeps them un-bundled. `gcode-parser`'s shipped ESM bundle declares a Transform-subclassing
stream class at module scope, which Rollup evaluates eagerly and which fails the production build
without these three polyfills; the dev server does not surface the same failure, so `npm run build` is
the only honest check.

**Step 2 — the bundled printing sample (D-07, D-08).** Hand-author
`public/gcode/print-sample.gcode`: millimetre units (G21), absolute distance mode (G90), the default XY
working plane (G17) stated explicitly, and an opening feed rate of 1200. Body is a print-style stack of
three closed square perimeters at increasing tool heights, each layer inset from the one below, the base
layer roughly 150 mm across in both X and Y, layer heights within the first few millimetres, and a final
retract to a clear height. The file must contain **exactly 7 G0 commands and exactly 12 G1 commands**,
with no G2/G3 anywhere, no plane-select other than G17, no inch mode, and no relative distance mode —
plan 02-02's test suite asserts those exact counts. The third layer's first cutting move carries an
inline feed rate of 900; every earlier motion command inherits 1200. Every rapid must actually change
position, so no motion command repeats the position already in force.

**Step 5 — `src/gcode/toolpath-anchor.ts` (D-06).** Import `RAIL_CENTER_X` from `../kinematics` and
`ROBOT_REACH_ENVELOPE`, `RIG_Z_OFFSET`, `CARRIAGE_TOP_Y` from `../scene/RailRig`. Export
`ROBOT_MOUNT_WORLD` as the world-space point the robot is bolted to — its components are `RAIL_CENTER_X`,
the carriage-top height constant, and `RIG_Z_OFFSET`, each imported, none retyped as a number. Export
`TOOLPATH_ANCHOR_OFFSET` as the world-space point the toolpath is anchored at: x is `RAIL_CENTER_X`, y is
the floor plane, z is `RIG_Z_OFFSET + ROBOT_REACH_ENVELOPE / 2`. Half the reach envelope, not the whole
envelope, places the work comfortably inside reach instead of exactly at its limit. Document the anchor
semantics precisely in a header comment, because Phase 3 consumes this as a stable contract: the
toolpath's own X and Z bounding-box centre is translated onto the anchor's X and Z, and the toolpath's
minimum Y (its deepest point) is translated onto the anchor's Y, so a milling sample's negative cut
depths rest at the floor plane rather than sinking below it. Also record in that comment that reach is
measured from `ROBOT_MOUNT_WORLD` and **not** from the ready-pose TCP — 02-CONTEXT.md's canonical refs
suggest deriving the anchor from `forwardKinematics(UR3E_READY_POSE)`, but the ready pose parks the arm
in the air roughly 0.85 m from this anchor, so a reach check taken from the TCP would fail for a pose
that is simply parked; the mounting point is the correct origin of the reach sphere. Record the
FK-derived ready-pose TCP world position in the same comment for Phase 3's benefit, together with the
composition that produces it: take `forwardKinematics(UR3E_READY_POSE).position` in the DH module's
z-up frame, apply the same `Rx(-90°)` frame rotation `RobotModel.tsx` applies to the loaded robot
(scene-local x is the DH x, scene-local y is the DH z, scene-local z is the negated DH y), then add
`RAIL_CENTER_X`, the carriage-top height and `RIG_Z_OFFSET` component-wise. Plan 02-02 asserts this
numerically.

**Step 6 — `src/gcode/parseToolpath.ts` (SIM-01).** This is the module Phase 3 reads, so its contract is
load-bearing. Export `type MoveClass = 'rapid' | 'cut'`; `interface ClassifiedSegment { type: MoveClass;
motion: 'G0' | 'G1' | 'G2' | 'G3'; source: 'line' | 'arc'; points: [number, number, number][];
feedRate: number | null }`; `interface ParsedToolpath { segments: ClassifiedSegment[]; unit: 'mm';
skippedMotionCount: number; appliedAnchorTranslation: [number, number, number]; bounds: { min: [number,
number, number]; max: [number, number, number] } | null }`; `function parseToolpath(gcodeText: string):
ParsedToolpath`; and `function toRenderBuckets(segments: readonly ClassifiedSegment[]): { rapidPoints:
[number, number, number][]; cuttingPoints: [number, number, number][] }`.

Implement `parseToolpath` as: (a) a feed-rate pre-scan using `parseStringSync` from `gcode-parser`,
carrying forward the last-seen F word and pushing one queue entry for every line that carries either a
motion word in the G0/G1/G2/G3 set or a bare X/Y/Z/I/J/K coordinate word — bare coordinate lines reuse
the previous motion mode and still fire a callback, so they must push an entry to keep the queue
aligned; (b) `new Toolpath({ addLine, addArcCurve }).loadFromStringSync(gcodeText)`, consuming the queue
by call order. Take the CW/CCW direction from `modal.motion`, never from a boolean parameter. Read the
feed rate **only** from the pre-scan queue: the interpreter's modal object carries a feed-*mode* flag
(G93/G94/G95), never a numeric rate, and an internal typo means even that field never updates from its
default — 02-RESEARCH.md Pitfall A. Leave the `addArcCurve` branch recording `skippedMotionCount` for
now; plan 02-02 fills it in with real tessellation.

Coordinate handling: convert millimetres to scene metres by dividing by exactly 1000, at one single
place in this module, with no rounding, truncation or clamping. Map g-code axes to scene axes with the
same handedness convention `RobotModel.tsx` uses — scene x is g-code x, scene y is g-code z, scene z is
the negated g-code y. Drop any segment whose start and end coincide. Compute the bounds over all
retained points, then apply the D-06 translation described in Step 5 to every point, and report the
translation actually applied on `appliedAnchorTranslation` so it is inspectable rather than implicit.
The returned `bounds` are the post-translation world-space bounds. Document on the `feedRate` field that
it is the modal F in force in the file's own units, that it is `null` until the file issues its first F
word, and that a rapid's real traverse rate is a machine property the file never states — so a consumer
must not use `feedRate` to time a rapid.

`toRenderBuckets` flattens each segment's `points` polyline into consecutive disjoint pairs (a polyline
of n points contributes 2·(n−1) entries) and routes it to `rapidPoints` when the type is rapid and
`cuttingPoints` otherwise. This is the pure, testable half of SIM-02.

**Step 7 — `src/store/cellStore.ts`.** Extend the existing store following its own field/action/comment
conventions. Add `export type ToolpathLoadStatus = 'idle' | 'parsing' | 'ready' | 'error'`, the fields
`selectedSampleId: string | null`, `toolpathLoadStatus: ToolpathLoadStatus`, `toolpath: ParsedToolpath |
null`, and an async action `selectSample(sampleId: string): Promise<void>` that resolves the sample from
`GCODE_SAMPLES`, sets the status to parsing, `fetch`es the sample's `filePath`, rejects a non-ok
response, calls `parseToolpath` on the response text, and stores the result with status ready — wrapping
the whole thing in try/catch so a parse failure lands on status error instead of throwing into React.
This is a once-per-selection write, which the file's own top-of-file rule explicitly permits; nothing
here may be written from a render frame.

**Step 8 — `src/ui/SampleSelect.tsx` (D-02).** A small controlled component that reads
`selectedSampleId` and `selectSample` from the store and renders a native `<select>` whose options come
from `GCODE_SAMPLES`, with a disabled placeholder option shown while nothing is selected. Use a native
`select` element rather than a registry component: `src/components/ui/` currently contains only
`button.tsx`, and the installed shadcn CLI is on the 4.x line whose preset flow diverges from the 3.8.4

**Step 9 — `src/scene/Toolpath.tsx` (SIM-02, D-03, D-04).** Read `toolpath` from the store, return null
when it is null, and otherwise derive `{ rapidPoints, cuttingPoints }` via `toRenderBuckets` inside a
`useMemo` keyed on the toolpath object so the batched geometries are rebuilt only when a new sample is
selected, never on an unrelated re-render. Render at most two drei `<Line>` elements, each with the
`segments` prop set so the flat point array is read as disjoint pairs — the default continuous mode
would draw phantom connectors across every gap between same-class moves. Guard each on its bucket being
non-empty so an all-rapid file mounts no cutting line at all. Define two module-level colour constants:
a muted gray for rapids and a warm orange for cutting moves (D-03) — both must read clearly against the
Dominant `#FAFAFA` background and the Secondary `#E4E7EB` floor, and must be distinguishable from the
Accent `#2563EB` for a colourblind viewer. The rapid line is `dashed` with a dash and gap size tuned to
the sample's actual on-screen scale; the cutting line is solid and slightly thicker (D-04), so the
distinction survives a greyscale still. Points arrive already anchored in world space, so this component
applies no group transform of its own.
